## 1. Что это за приложение

Trinotify — Android-приложение без требования root-прав, которое перехватывает
все уведомления и входящие звонки на устройстве и решает по каждому событию:
пропустить со звуком, показать беззвучно или заблокировать полностью.

Основные возможности:

- **Перехват уведомлений** от всех установленных приложений в реальном времени.
- **Правила по приложению**: со звуком / тихо / блокировать / решает ML.
- **Правила по отправителю**: срабатывают по подстроке в заголовке или тексте,
  с опциональной привязкой к конкретному приложению.
- **Блокировка несмахиваемых уведомлений** — включая постоянные «демоны»
  сторонних приложений.
- **Архив** всех уведомлений и звонков в локальной базе с поиском и фильтрами.
- **Ручная разметка** записей архива, которая служит обучающей выборкой.
- **Классификатор на наивном Байесе**, обучаемый на этой разметке.
- **Фильтр звонков** — чёрный или белый список номеров с поддержкой
  международных форматов и шаблонов.
- **Быстрые режимы** (обычный / вибро / тихий) прямо из шторки уведомлений.
- **Ночной режим** по расписанию с ручным приоритетом.
- **Собственная озвучка**: выбор мелодии, громкости, режима «звук/вибрация».
- **Опциональное шифрование архива** (SQLCipher + Android Keystore).
- **Опциональный вход по биометрии или пину** устройства.
- **Экспорт и импорт** правил и обучающей выборки в JSON.

## 2. Ключевая идея и главное ограничение Android

### Почему нельзя просто «заглушить» чужое уведомление

Android устроен так, что звук уведомления проигрывает **система** в момент
публикации, ещё до того как сторонний слушатель успевает отреагировать. API
`NotificationListenerService` даёт возможность **прочитать** и **удалить**
уведомление, но не даёт возможности отменить уже начатый звук или подавить его
заранее.

Следствие: подход «перехватить и решить, звучать ли» технически невозможен в
том виде, в каком он кажется очевидным.

### Принятое решение

Приложение работает по схеме «глушим всё системно — озвучиваем сами»:

1. Trinotify включает системный режим «Не беспокоить» (DND) с политикой
   приоритетов, при которой уведомления показываются, но не звучат.
2. Все чужие уведомления таким образом становятся беззвучными.
3. Уведомления, которые прошли правила как разрешённые, Trinotify озвучивает
   самостоятельно — собственным проигрывателем.

Этот компромисс был явно согласован при постановке задачи: «допустимо заглушить
всё, кроме моего приложения, если других вариантов нет».

Побочный эффект — постоянная иконка «Не беспокоить» (луна) в статус-баре.
Убрать её невозможно: индикаторы системных режимов рисует SystemUI, и
стороннее приложение не имеет к ним доступа.

## 3. Технологический стек

| Компонент | Выбор | Обоснование |
|---|---|---|
| Язык | Kotlin | Нативный язык Android; нужные API (`NotificationListenerService`, `CallScreeningService`) — часть платформы |
| UI | Jetpack Compose + Material 3 | Декларативный UI, меньше кода, состояние в одном месте |
| БД | Room 2.6.1 поверх SQLite | Типобезопасные запросы, реактивные `Flow`, миграции |
| Шифрование БД | SQLCipher (`net.zetetic:sqlcipher-android:4.6.1`) | Прозрачное для Room шифрование файла базы |
| Криптоключи | Android Keystore (AES-256-GCM) | Ключ не покидает аппаратное хранилище |
| Биометрия | `androidx.biometric:biometric:1.1.0` | Единый API для отпечатка, лица и пина |
| Кодогенерация | KSP + Room compiler | Быстрее KAPT |
| ML | Собственный наивный Байес | Обучается мгновенно на десятках примеров, не требует зависимостей |
| Тесты | JUnit 4 | Чистая логика вынесена из Android-зависимостей |

Целевые версии: `compileSdk 34`, `minSdk 29` (Android 10), `targetSdk 34`,
JVM target 17.

## 5. Слой данных

### 5.1 Сущности (`Entities.kt`)

**Константы действий** (`object Action`):

| Константа | Значение | Смысл |
|---|---|---|
| `ALLOW` | со звуком | показать и озвучить |
| `SILENCE` | тихо | показать без звука |
| `BLOCK` | блокировать | скрыть/закрыть уведомление |
| `ML` | решает модель | делегировать классификатору (только для правил приложений) |
| `DEFAULT` | нет правила | использовать действие по умолчанию |

**`NotifRecord`** — запись архива (таблица `notif`):

| Поле | Тип | Назначение |
|---|---|---|
| `id` | Long, автоинкремент | первичный ключ |
| `pkg` | String | пакет приложения (`call` для звонков) |
| `appLabel` | String | человекочитаемое имя приложения |
| `title` | String | заголовок уведомления / номер телефона |
| `text` | String | текст уведомления |
| `postedAt` | Long | момент события, мс |
| `verdict` | String | принятое действие |
| `verdictSource` | String | объяснение: какое правило сработало |
| `userLabel` | String? | ручная метка пользователя (обучающая выборка) |
| `isCall` | Boolean | это звонок, а не уведомление |

Поле `verdictSource` существует ради прозрачности: пользователь всегда видит,
почему уведомление получило именно этот вердикт («Правило приложения»,
«ML (80%)», «По умолчанию»).

**`AppRule`** (таблица `app_rule`) — правило для приложения целиком.
Первичный ключ — `pkg`. Поле `hits` считает срабатывания.

**`SenderRule`** (таблица `sender_rule`) — правило по содержимому:
`pattern` (подстрока), `pkg` (null = любое приложение), `inText` (искать ли
в тексте, а не только в заголовке), `action`, `hits`.

**`CallRule`** (таблица `call_rule`) — правило для номера: `pattern`,
`action` (`ALLOW`/`BLOCK`), `hits`.

**`BayesToken`** (таблица `bayes`) — счётчики модели. Составной первичный ключ
`(token, label)`. Специальный токен `__doc__` хранит число документов класса.

### 5.2 Запросы (`Daos.kt`)

`NotifDao`:
- `recent()` — реактивный `Flow` последних 1500 записей для экрана архива;
- `insert`, `insertAll` — запись событий и импорт;
- `setLabel(id, label)` — ручная разметка;
- `labeled()` — вся обучающая выборка;
- `labeledCount()` — реактивный счётчик для интерфейса;
- `pruneUnlabeled(before)` — авточистка старых неразмеченных;
- `clearUnlabeled()`, `clearAll()` — ручная очистка;
- `allRecords()` — полный дамп для бэкапа.

`RuleDao` — CRUD по трём типам правил плюс инкременты счётчиков
(`incAppHit`, `incSenderHit`, `incCallHit`) и снапшоты для кэша.

`BayesDao` — `clear`, `insertAll`, `all`: модель всегда переобучается целиком,
инкрементального обновления нет (при десятках-сотнях примеров это дешевле и
надёжнее).

### 5.3 База (`Db.kt`)

Room-база версии 2 с пятью сущностями. Существует в двух вариантах файла:

- `trinotify.db` — обычная;
- `trinotify_enc.db` — зашифрованная SQLCipher.

**Миграция 1→2** добавляет колонки `hits` во все три таблицы правил. Важно:
`fallbackToDestructiveMigration` был убран — потеря пользовательских данных
при обновлении схемы недопустима.

**`openOrRecover`** — защита от «крэш-петли». База открывается и сразу
проверяется тестовым запросом (`SELECT count(*) FROM sqlite_master`). Если
зашифрованная база нечитаема (ключ Keystore пропал после очистки данных,
файл повреждён, переключение шифрования оборвалось) — ключ сбрасывается,
файл удаляется, приложение стартует с чистой незашифрованной базой. Без этого
приложение падало бы бесконечно.

**`switchEncryption(enable)`** — перенос данных между вариантами:
1. читает все записи, правила и модель из текущей базы;
2. удаляет целевой файл (страховка от дублей после прерванной попытки);
3. при включении шифрования генерирует свежий ключ;
4. записывает данные в новую базу;
5. переключает флаг и удаляет старый файл.

Правила отправителей и звонков переносятся с `id = 0`, чтобы Room присвоил
новые автоинкрементные идентификаторы.

### 5.4 Настройки (`Prefs.kt`)

| `mlThreshold` | Float | 0.75 | порог уверенности классификатора |
| `ringInDnd` | Bool | true | свой рингтон при входящем звонке |
| `callAlertMode` | String | BOTH | звонок: звук/вибрация/оба |
| `callRingUri` | String | "" | мелодия звонка (пусто = встроенная) |
| `callVolume` | Float | 1.0 | громкость звонка |

### 5.5 Хранилище ключа (`KeyVault.kt`)

Пароль базы — 32 случайных байта от `SecureRandom`. Сам пароль хранится
зашифрованным: мастер-ключ AES-256-GCM создаётся в **Android Keystore**
(`AndroidKeyStore`), где он неизвлекаем даже при физическом доступе к файлам.

Формат хранения: `Base64(IV || ciphertext)` в отдельном файле настроек.
IV длиной 12 байт генерируется системой на каждое шифрование, тег
аутентификации — 128 бит.

Функция `reset()` удаляет и запись пароля, и сам ключ из Keystore — нужна при
восстановлении после повреждения базы.

**Важное архитектурное решение**: ключ базы доступен приложению *без*
подтверждения биометрией. Иначе фоновый сервис не смог бы работать до первой
разблокировки. Биометрия защищает **вход в интерфейс**, а шифрование защищает
**файл на диске**. Это разные задачи, и объединять их нельзя без потери
фоновой работы.

## 6. Логика принятия решений

### 6.1 Движок (`RuleEngine.kt`)

Класс `RuleEngine` возвращает `Decision(action, source)` — действие и текстовое
объяснение. Приоритет проверок:

1. **Правила отправителей** — самые точные. Перебираются все; если у правила
   указан пакет, оно применяется только к нему. Ищется подстрока без учёта
   регистра в заголовке, а при `inText = true` — и в тексте.
2. **Правило приложения** — если действие `ML`, включается делегирование
   классификатору; иначе действие возвращается сразу.
3. **ML-классификатор** — если включён глобально или назначен приложению.
   Результат принимается, только если уверенность не ниже порога.
4. **Действие по умолчанию** из настроек.

Счётчики срабатываний инкрементируются в отдельном фоновом скоупе
(`hitScope`), чтобы запись в базу не задерживала решение по уведомлению.

### 6.2 Кэш правил (`RuleCache.kt`)

Правила читаются на **каждое** уведомление и **каждый** звонок, поэтому они
держатся в памяти:

- три реактивных подписки на `Flow` из Room обновляют кэш при любом изменении;
- если база временно недоступна (зашифрована и устройство ещё не
  разблокировано), подписка повторяется каждые 5 секунд;
- `callRulesNow()` — синхронный доступ для фильтра звонков; при холодном старте
  делает одно блокирующее чтение как запасной вариант.

Это устранило две проблемы: обращения к базе в горячем пути и `runBlocking`
в фильтре звонков, где у системы жёсткий таймаут на вердикт.

### 6.3 Сопоставление номеров (`CallMatcher`)

Телефонные номера приходят в непредсказуемых форматах. Алгоритм:

1. `normalize()` оставляет только цифры; российские 11-значные номера с ведущей
   `8` приводятся к `7`.
2. Если в шаблоне есть `*` — он превращается в регулярное выражение, где
   каждая часть экранируется (`Regex.escape`), а `*` заменяется на `.*`.
   Проверяются обе формы записи номера.
3. Полные номера (7+ цифр) сравниваются **по общему хвосту** длиной до 10
   цифр. Это делает сравнение независимым от кода страны и формата:
   `+375 29 123-45-67`, `375291234567` и `291234567` совпадают между собой.
4. Короткие шаблоны (например `8800`) ищутся как подстрока.

Экранирование частей шаблона исключает инъекцию регулярных выражений через
пользовательский ввод.

## 7. Машинное обучение

### 7.1 Модель

Реализован **мультиномиальный наивный Байес** — статистический классификатор,
подходящий для коротких текстов и малых выборок.

Класс `BayesCore` содержит только математику и не зависит от Android, что
позволяет покрыть его юнит-тестами.

**Токенизация** (`tokenize`):
- заголовок и текст приводятся к нижнему регистру;
- выделяются последовательности букв и цифр (`[\p{L}\p{N}]+`);
- отбрасываются токены короче 2 и длиннее 24 символов;
- берутся первые 80 токенов;
- добавляется токен `pkg:<пакет>` **трижды** — приложение задано как ключевой
  признак по требованию к продукту.

**Классификация**: для каждого класса считается логарифм апостериорной
вероятности со сглаживанием Лапласа (`+1` в числителе, размер словаря в
знаменателе). Сглаживание обязательно: без него один незнакомый токен обнулял
бы вероятность целого класса. Логарифмы используются, чтобы не столкнуться с
исчезновением порядка при перемножении сотен малых чисел.

Результат нормализуется через `softmax` с вычитанием максимума (защита от
переполнения экспоненты) и возвращается как пара «метка, уверенность 0..1».

Если классов меньше двух, классификатор возвращает `null` — обучать
разделение не на чем.

### 7.2 Обучение

`Ml.rebuild(db)` — полное переобучение:
1. читает все размеченные записи;
2. считает документы и частоты токенов по классам;
3. полностью перезаписывает таблицу `bayes`;
4. строит модель в памяти.

`rebuildAsync` запускает переобучение в собственном скоупе, не привязанном к
экрану. Это исправило реальный дефект: при разметке из архива обучение
запускалось в скоупе Compose-экрана, и уход с экрана мог оборвать корутину
между очисткой таблицы и записью новых счётчиков, оставляя пустую модель.

### 7.3 Почему именно наивный Байес

Альтернативы рассматривались:

- **Деревья решений / градиентный бустинг** — выигрывают на сотнях и тысячах
  примеров, требуют тяжёлого обучения и настройки. На десятках примеров
  преимущества нет.
- **Нейросетевые эмбеддинги** — понимают синонимы и смысл, но это десятки
  мегабайт модели, TFLite и медленное дообучение на устройстве.

Наивный Байес обучается мгновенно на любом объёме разметки, работает за
микросекунды, не добавляет зависимостей и обобщает на незнакомые тексты.
Наиболее выгодное направление развития — не смена алгоритма, а биграммы
(пары слов) и отдельные априорные вероятности по приложениям.

## 8. Фоновые сервисы

### 8.1 Перехватчик уведомлений (`NotifierListener.kt`)

Наследник `NotificationListenerService` — центральный компонент приложения.

**Жизненный цикл.** В `onListenerConnected` сервис:
- применяет политику DND;
- показывает постоянное уведомление статуса;
- регистрирует приёмник состояния телефона (`PHONE_STATE`);
- регистрирует приёмник тика системных часов (`TIME_TICK`, раз в минуту);
- загружает ML-модель и выполняет авточистку архива;
- запускает зачистку уже висящих уведомлений.

**Обработка уведомления** (`onNotificationPosted`):

1. Пропускаются собственные уведомления приложения.
2. Извлекаются заголовок и текст (`EXTRA_TITLE`, `EXTRA_TEXT`/`EXTRA_BIG_TEXT`).
3. Проверяется **защищённость**: уведомления категории `CATEGORY_CALL` и
   пакетов телефонии (`com.android.server.telecom`, `com.android.phone`)
   никогда не блокируются — гашение уведомления дайлера ломает входящий вызов.
4. Проверяется **медиаплеер**: категория `CATEGORY_TRANSPORT` или наличие
   `EXTRA_MEDIA_SESSION`. Это транспортные контролы (музыка, голосовые, видео),
   а не сообщения: они не озвучиваются, не попадают в архив и не подпадают под
   действие по умолчанию. Работает только явное правило «Блокировать».
5. Вычисляется вердикт движком правил.
6. При `BLOCK` уведомление удаляется: смахиваемое — через `cancelNotification`,
   несмахиваемое — через `snoozeNotification` на ~10 лет.
7. Запись помещается в архив, если это не дубликат и не пустая сводка группы.
8. Разрешённое уведомление озвучивается, если активен режим тишины.

Вся работа обёрнута в `try/catch`: при зашифрованной базе до первой
разблокировки устройства Keystore закрыт, и без перехвата исключения процесс
слушателя падал бы в бесконечной петле перезапусков.

**Подавление повторов.** Две отдельные защиты:
- флаг `FLAG_ONLY_ALERT_ONCE` — приложение само просит не тревожить при
  обновлениях (прогресс загрузки, статусы); такие обновления не звучат и не
  архивируются;
- отложенное забывание: при удалении уведомления запись о его содержимом
  живёт ещё 20 секунд. Цикл «отмена + перепост того же» (частый на MIUI после
  выгрузки приложения из памяти) больше не воспринимается как новое событие.

**Зачистка (`sweepActive`).** Применяет правила к уже висящим уведомлениям —
это то, что позволяет убрать постоянные «демоны» сторонних приложений.
Работает в обе стороны:
- блокирует то, что должно быть заблокировано;
- возвращает из отложенного состояния то, что больше блокироваться не должно.

Критично: обратный ход трогает **только собственные снузы**, ключи которых
хранятся в множестве `ourSnoozes`. Иначе приложение возвращало бы уведомления,
отложенные самим пользователем через шторку, ломая штатную функцию системы.

### 8.2 Управление DND (`Dnd.kt`)

Устанавливает `NotificationManager.Policy` с приоритетными категориями:
будильники, медиа, система, звонки и повторные звонящие. Визуальные эффекты не
подавляются (`suppressedVisualEffects = 0`) — уведомления должны быть видны,
просто беззвучны.

Фильтр прерываний переключается между `INTERRUPTION_FILTER_PRIORITY` (режим
тишины включён) и `INTERRUPTION_FILTER_ALL` (выключен).

### 8.3 Кнопки режимов (`QuickModeReceiver.kt`)

Приёмник не экспортирован (`android:exported="false"`), поэтому недоступен
сторонним приложениям. Значение режима дополнительно проверяется по белому
списку. Каждой кнопке соответствует собственный `action`
(`com.trinotify.app.QUICK_MODE.<режим>`) и собственный `requestCode` — это
исключает коллизии `PendingIntent`, которые иначе различались бы только
дополнительными данными.

## 9. Звук, вибрация и аудиофокус

Объект `Sounder` — самая насыщенная нюансами часть приложения.

### 9.1 Каналы уведомлений

| Канал | Важность | Назначение |
|---|---|---|
| `trinotify_status_v1` | MIN | постоянное уведомление «сервис активен» с кнопками режимов |
| `trinotify_mirror_v2` | HIGH, bypassDnd | зеркальные уведомления со звуком |
| `trinotify_mirror_muted_v1` | LOW, без звука | повторы в пачке (видны, но не звучат) |

### 9.2 Выбор источника звука

Функция `candidates()` строит цепочку запасных вариантов: выбранный
пользователем звук → встроенный (`res/raw`) → системный по умолчанию → первые
стандартные из списка.

Цепочка обязательна из-за реального дефекта: мелодии тем MIUI лежат в
`/data/system/theme_magic/` и **недоступны другим приложениям** из-за политики
SELinux. Проигрыватель молча не открывал файл — была вибрация, но не было
звука. Теперь недоступный источник просто пропускается.

Встроенные звуки: `hotline_miami_ii_wrong_number_blizzard.mp3` (звонок) и
`sims_3_opportunity.mp3` (уведомления).

### 9.3 Поток воспроизведения

Звук идёт через **поток будильника** (`USAGE_ALARM`). Причины:
- DND его не глушит;
- он не зависит от громкости медиа, которая часто убавлена.

Ползунки громкости в настройках задают долю от системной громкости будильника.

### 9.4 Аудиофокус

Проигрывание запрашивает аудиофокус: для звонка — эксклюзивный
(`AUDIOFOCUS_GAIN_TRANSIENT`), для уведомления — с приглушением чужой музыки
(`AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`).

Возврат фокуса гарантируется тремя независимыми механизмами:

1. **Колбэк завершения** трека.
2. **Колбэк ошибки** проигрывателя.
3. **Сторожевой таймер** — отпускает фокус через длительность трека + 1 секунда
   (или 10 секунд, если длительность неизвестна).

Плюс счётчик поколений (`playbackGen`): колбэк старого трека не отнимает фокус
у нового, если за это время началось новое воспроизведение.

Это исправило реальный дефект: поле проигрывателя писалось из фонового потока,
а колбэк читал его из главного; без `@Volatile` сравнение могло дать ложный
результат, фокус не возвращался, и звук стороннего приложения (например
TikTok) оставался приглушённым до перезапуска. Теперь поле помечено
`@Volatile`, а все операции с фокусом синхронизированы.

### 9.5 Объединение звуков

Пачка уведомлений, пришедших почти одновременно, не должна превращаться в
какофонию. Окно объединения — 1200 мс: в его пределах звучит только первое
оповещение. В режиме зеркальных уведомлений остальные показываются через
беззвучный канал, то есть видны, но не звучат повторно.

Кнопка «Проверить» в настройках обходит окно через флаг `testBypass`.

### 9.6 Собственный рингтон

MIUI при любом активном DND глушит системный рингтон, игнорируя политику
«звонки от всех» — это подтверждено логом Telecom (`isRingerAudible: 0`).
Поэтому при входящем звонке в режиме тишины Trinotify играет мелодию сам,
зациклено, с вибрацией по шаблону 700/800 мс, и останавливается при ответе или
завершении вызова. Страховка — принудительная остановка через 60 секунд.

## 10. Режимы и расписание

Объект `Modes` реализует три быстрых режима:

| Режим | Поведение |
|---|---|
| `NORMAL` | звуки как настроено |
| `VIBRATE` | уведомления и звонки только вибрацией |
| `SILENT` | полная тишина (уведомления видны, звонки не звенят) |

### 10.1 Ночное расписание

Ночное окно задаётся минутами от полуночи и **может проходить через полночь**:

```kotlin
if (startMinutes < endMinutes) nowMinutes >= startMinutes && nowMinutes < endMinutes
else nowMinutes >= startMinutes || nowMinutes < endMinutes
```

Вырожденное окно (начало равно концу) ночью не считается.

### 10.2 Ручной приоритет

Изначально расписание жёстко перекрывало ручной выбор, и ночью режим нельзя
было переключить. Сейчас: нажатие кнопки в шторке или выбор в настройках во
время ночи устанавливает `nightOverrideUntil` в момент окончания текущего
ночного окна. Действующий режим вычисляется так:

```kotlin
if (night && !manualOverride) nightMode else quickMode
```

Приоритет истекает сам вместе с ночным окном, следующей ночью расписание снова
вступает в силу. Изменение самого расписания сбрасывает приоритет.

### 10.3 Актуальность статуса

Постоянное уведомление показывает действующий режим и контекст: «ночь до
08:00», «вручную до 08:00» или «ночь с 23:00». Чтобы граница ночного окна
отражалась вовремя, сервис подписан на тик системных часов и перерисовывает
статус раз в минуту — но только если текст действительно изменился
(кэш `lastStatusText`).

## 11. Фильтрация звонков

`CallScreener` — наследник `CallScreeningService`. Работает, когда приложению
выдана роль «Определитель номера и защита от спама»
(`RoleManager.ROLE_CALL_SCREENING`).

Логика вердикта:

```kotlin
val block = when {
    !prefs.enabled -> false
    allowRule != null -> false          // «Пропускать» всегда сильнее
    whitelistMode -> true               // белый список: блокируем всё остальное
    else -> blockRule != null           // чёрный список
}
```

Правило «Пропускать» приоритетнее правила «Блокировать» — это позволяет
заблокировать диапазон `8800*`, но пропустить конкретный номер из него.

Режим белого списка включается либо настройкой `callMode = WHITELIST`, либо
ночью при включённом `nightCallsWhitelistOnly`.

Заблокированный вызов отклоняется молча: `setDisallowCall(true)`,
`setRejectCall(true)`, `setSkipNotification(true)`. Все звонки при включённом
`logCalls` попадают в архив с пометкой источника решения.

Важное системное ограничение: звонки от номеров **из списка контактов** Android
вообще не передаёт в фильтр — они проходят всегда. Экстренные вызовы также не
проходят через `CallScreeningService`.

## 12. Пользовательский интерфейс

Четыре вкладки в нижней навигации: Архив, Приложения, Правила, Настройки.
Тема Material 3 с бирюзовым акцентом, автоматически светлая или тёмная.

### 12.1 Архив (`ArchiveScreen.kt`)

Список последних 1500 записей с поиском по приложению, заголовку, тексту и
пакету, плюс фильтры «Звонки» и «Размеченные».

Диалог записи содержит:
- текст уведомления в **прокручиваемой области фиксированной высоты** (150 dp),
  чтобы длинные сообщения не выталкивали кнопки за экран;
- метаданные: пакет, время, вердикт с источником;
- чипы разметки для ML: со звуком / тихо / блокировать / без метки;
- чипы правила для приложения (все пять действий, текущее подсвечено);
- чипы быстрого создания правила отправителя, **привязанного к пакету** —
  безопасный вариант, устойчивый к подделке имени отправителя.

Любое изменение правила немедленно запускает зачистку висящих уведомлений.

### 12.2 Приложения (`AppsScreen.kt`)

Список установленных приложений с иконками и поиском. Приложения с правилами
поднимаются наверх, системные без правил уходят вниз. Выбор действия — через
выпадающее меню. Список кэшируется на время жизни процесса
(`AppListCache`), поскольку загрузка сотен приложений занимает заметное время.

### 12.3 Правила (`RulesScreen.kt`)

Управление правилами отправителей и звонков. У каждого правила показан счётчик
срабатываний — видно, какие правила работают, а какие мертвы.

При создании правила отправителя **без указания пакета** выводится
предупреждение: любое приложение может поставить уведомление с таким же
заголовком и тем самым сработать по чужому правилу.

### 12.4 Настройки (`SettingsScreen.kt`)

Вместо одного длинного списка тумблеров — карточка состояния и шесть
категорий, каждая со своим подэкраном:

| Категория | Содержимое |
|---|---|
| Основное | режим тишины, действие по умолчанию, быстрый режим |
| Звук и вибрация | рингтон, мелодии, громкости, способ озвучки, тесты |
| Ночной режим | расписание, режим ночью, белый список звонков ночью |
| Машинное обучение | включение, порог, статистика, переобучение |
| Данные и приватность | авточистка, бэкап, экспорт/импорт, очистка, шифрование, замок |
| Разрешения | статусы всех разрешений с кнопками выдачи |

Навигация назад обрабатывается системной кнопкой (`BackHandler`).

Выбор звука: системный пикер мелодий, произвольный файл (копируется во
внутреннее хранилище, чтобы всегда оставаться читаемым) или возврат к
встроенному. Кнопка «Проверить» работает как переключатель с автостопом
через 15 секунд.

## 13. Приватность и безопасность

Приложение по своей природе видит крайне чувствительные данные: переписку,
коды подтверждения, номера звонящих. Меры защиты:

### 13.1 Данные не покидают устройство

Нет ни одного сетевого вызова. Никакой аналитики, никакой телеметрии.

`allowBackup="false"`, `fullBackupContent="false"` и явные правила
`data_extraction_rules.xml` исключают архив из облачного бэкапа Google и
переноса на другое устройство. Без этого база с перепиской уходила бы на
чужие серверы в обход собственного шифрования.

### 13.2 Шифрование архива

Опциональное: SQLCipher шифрует файл базы целиком, ключ защищён аппаратным
Keystore. Веса ML-модели при этом продолжают работать — Room читает таблицу
`bayes` как обычно, шифрование прозрачно.

Ограничение, о котором честно сказано в интерфейсе: после перезагрузки
телефона до первой разблокировки экрана Keystore закрыт, база недоступна, и в
это окно фильтрация работает по действию по умолчанию, без архивации.

### 13.3 Замок интерфейса

Опциональный вход по биометрии или коду блокировки устройства
(`BiometricPrompt` с `BIOMETRIC_WEAK or DEVICE_CREDENTIAL`). Повторный запрос
только после минуты вне приложения, чтобы системные пикеры не требовали
подтверждения на каждый возврат.

При включённом замке окно помечается `FLAG_SECURE`: содержимое не попадает ни
в превью «Недавних», ни в скриншоты.

### 13.4 Устойчивость к чужому вводу

- Все запросы к базе параметризованы (Room) — SQL-инъекция невозможна.
- Шаблоны номеров экранируются перед превращением в регулярное выражение.
- Имена файлов при копировании звуков очищаются от небезопасных символов.
- Приёмник кнопок режимов не экспортирован и валидирует значение.
- Импортируемый JSON разбирается с проверкой сигнатуры приложения и
  безопасными значениями по умолчанию для отсутствующих полей.

### 13.5 Секреты сборки

Пароли подписи вынесены в `keystore.properties`, который вместе с файлами
`*.keystore`/`*.jks` внесён в `.gitignore`. Сборка читает их через
`rootProject.file(...)` и корректно работает без них — тогда release просто не
подписывается.

## 14. Экспорт, импорт и обслуживание архива

Объект `DataIO` работает через системный выбор файлов (SAF), поэтому не
требует разрешений на доступ к хранилищу.

**Экспорт** — два режима:
- *правила и датасет*: все правила плюс только размеченные записи;
- *полный бэкап*: дополнительно весь архив.

Формат — JSON с полями `app`, `version`, `exportedAt` и массивами правил и
записей.

**Импорт** проверяет сигнатуру `app == "trinotify"`, добавляет правила
(правило приложения перезаписывает существующее, правила отправителей и
звонков дедуплицируются по содержимому), вставляет записи и переобучает модель.

**Обслуживание архива**:
- авточистка неразмеченных записей старше 7/30/90 дней (по умолчанию
  выключена);
- ручная очистка только неразмеченных — датасет для ML сохраняется;
- полная очистка архива.

Размеченные записи не удаляются автоматически никогда: это обучающая выборка,
собранная вручную.

## 15. Разрешения

| Разрешение / доступ | Зачем | Как выдаётся |
|---|---|---|
| Доступ к уведомлениям | чтение и удаление уведомлений | системный экран слушателей |
| `ACCESS_NOTIFICATION_POLICY` | управление «Не беспокоить» | системный экран политики |
| Роль `CALL_SCREENING` | фильтрация звонков | системный запрос роли |
| `READ_PHONE_STATE` | определение входящего вызова для своего рингтона | обычный запрос |
| `POST_NOTIFICATIONS` | собственные уведомления (Android 13+) | обычный запрос |
| `VIBRATE` | вибрация | автоматически |
| `QUERY_ALL_PACKAGES` | список приложений для правил | автоматически |
| Игнорирование оптимизации батареи | выживание сервиса | системный диалог |
| Автозапуск MIUI | выживание сервиса после перезагрузки | вручную в настройках MIUI |

Экран «Разрешения» показывает актуальный статус каждого и обновляет его при
возврате на экран.

## 16. Сборка и подпись

```
gradle assembleDebug        # отладочная сборка
gradle assembleRelease      # подписанная релизная сборка
```

Структура Gradle: `settings.gradle.kts` объявляет плагины (AGP 8.6.1,

## 18. Особенности MIUI

Отдельный раздел, потому что оболочка Xiaomi заметно отличается от чистого
Android, и часть решений продиктована именно ею.

1. **Рингтон при DND.** MIUI глушит системный звонок, игнорируя политику
   «звонки от всех». Обход — собственный проигрыватель на потоке будильника.
2. **Мелодии тем недоступны.** Файлы в `/data/system/theme_magic/` закрыты
   политикой SELinux, что требует цепочки запасных источников звука.
3. **Автозапуск.** Без него система выгружает сервис; включается вручную или
   через `adb shell appops set com.trinotify.app 10008 allow`.
4. **Перепост уведомлений.** MIUI чаще пересоздаёт уведомления после выгрузки
   приложений, что и потребовало отложенного забывания содержимого.

## 19. Известные ограничения

Честный список того, чего приложение не может:

- **Иконки статус-бара** (луна DND, беззвучный режим) убрать невозможно — их
  рисует система, стороннего API нет.
- **Звонки от контактов** не проходят через фильтр — ограничение Android.
- **Экстренные вызовы** не фильтруются (и не должны).
- **Окно после перезагрузки**: при включённом шифровании до первой
  разблокировки экрана база недоступна.
- **Правило отправителя без указания пакета** может быть спровоцировано любым
  приложением, поставившим уведомление с таким заголовком; интерфейс об этом
  предупреждает.
- **Экспортируемый JSON не шифруется** — это осознанное решение ради
  переносимости, но файл содержит тексты переписки.
- **Минификация выключена**, обратная разработка тривиальна; для личного
  приложения это принято сознательно.
- Приложение **не заменяет** системные средства защиты и не блокирует
  уведомления до их появления — только после.

## Итог

Trinotify решает задачу, которая на первый взгляд невозможна без root: выборочно
пропускать одни уведомления и глушить другие. Решение построено на честном
компромиссе — системный режим «Не беспокоить» глушит всё, а приложение
самостоятельно озвучивает то, что прошло правила.

Вокруг этой идеи выстроены слои: правила по приложению и отправителю, локальный
классификатор, обучаемый вручную размеченными данными, фильтр звонков с
поддержкой международных форматов, режимы и расписание, а также средства
приватности — шифрование архива, замок интерфейса и полный запрет облачного
бэкапа.

Значительная часть кода посвящена не основной логике, а обходу реальных
особенностей платформы и оболочки: недоступным файлам мелодий, глушению
рингтона, перепостам уведомлений, возврату аудиофокуса и гонкам между
потоками. Каждое такое место снабжено комментарием с объяснением причины —
чтобы при последующих правках обход не был случайно удалён как «лишний».
